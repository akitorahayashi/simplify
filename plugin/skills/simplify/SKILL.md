# 変更コードのクリーンアップレビュー

変更されたコードの品質を上げることだけを扱う。正しさのバグは探さない。バグの発見が目的の依頼は、このスキルではなくコードレビュー用の手段が担う（Claude Code では `/code-review`）。

## 対象範囲の取得

レビュー対象は差分であり、次の順で取得する。

1. `git diff @{upstream}...HEAD`
2. upstream が設定されていない場合は `git diff main...HEAD`、それも取れない場合は `git diff HEAD~1`
3. 未コミットの変更がある場合、または 1 と 2 の差分が空だった場合は `git diff HEAD` も取得し、作業ツリーの変更を対象に含める

引数で PR 番号、ブランチ名、ファイルパスが渡された場合は、上記に代えてその対象の差分をレビュー範囲とする。

いずれの経路でも差分が空の場合は、レビュー対象が無いことを報告して終了する。範囲を推測で広げない。

## 4観点のレビュー

差分を再利用、単純化、効率、抽象度の4観点でレビューする。各観点は他の観点の結果を参照せず、独立に差分全体を見る。

実行形態は環境によって決まる。

- サブエージェントを起動する手段がある環境では、4観点を1メッセージでまとめて起動し、並列に実行する。各サブエージェントには差分と担当する1観点だけを渡す。
- その手段が無い環境では、4観点を順に自分で実行する。この場合は最終報告に、並列実行ではなく逐次実行したことを明記する。

各観点は指摘ごとに、ファイル、行、1行の要約、そして具体的なコスト（何が重複しているか、何が無駄になっているか、何が保守しにくくなるか）を返す。

### 再利用

差分が持ち込んだ、既存実装の焼き直しを指摘する。共有モジュールと変更箇所の近傍ファイルを検索し、代わりに呼ぶべき既存の実装を名指しする。

### 単純化

差分が持ち込んだ不要な複雑さを指摘する。冗長な状態や他から導出できる状態、わずかな差異を持つコピー＆ペースト、深いネスト、置き去りにされた死んだコードが対象で、同じ仕事をする、より単純な形を示す。

### 効率

差分が持ち込んだ無駄な処理を指摘する。重複した計算や繰り返しの I/O、直列に並べられた独立処理、起動処理やホットパスに足されたブロッキング処理が対象で、より安価な代替を示す。

クロージャや捕捉した環境から作られる長寿命オブジェクトも対象とする。これは囲みスコープ全体をオブジェクトの寿命だけ延命させ、そのスコープが大きな値を保持している場合はメモリリークになる。必要なフィールドだけを複製するクラスや構造体への置き換えを示す。

### 抽象度

各変更が適切な深さで実装されているかを確認する。共有基盤の上に積まれた特殊ケースは、修正が浅すぎることの兆候であり、特殊ケースの追加ではなく基盤側の一般化を示す。

## 修正の適用

4観点すべての結果が揃ってから着手する。同じ行、または同じ仕組みを指す指摘は1件に統合する。

残った指摘は、その場でコードを直す。次のいずれかに当たる指摘は直さず、スキップした事実を記録する。指摘への反論は書かない。

- 修正が、意図された挙動を変えてしまうもの
- 修正が、レビュー範囲から大きく外れた変更を必要とするもの
- 誤検知と判断したもの

最後に、直したものとスキップしたものを短くまとめる。指摘が1件も残らなかった場合は、コードがすでに整っていることを述べる。

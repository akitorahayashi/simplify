# 変更コードのクリーンアップレビュー

レビュー範囲の意図された挙動を保ったまま、コードの品質を上げる。

## 対象範囲の取得

引数で PR 番号、ブランチ名、ファイルパスが渡された場合は、その対象の差分をレビュー範囲とする。

引数が無い場合は、比較元のベースブランチを次の順で決める。

1. `gh` が使えて現在のブランチに PR がある場合は、その base ブランチ（`gh pr view --json baseRefName -q .baseRefName`）
2. `git symbolic-ref --quiet --short refs/remotes/origin/HEAD` が指す既定ブランチ
3. 2 が解決できない場合は、リモートに存在する `main`、無ければ `master`

決まったベースに対して `git diff <base>...HEAD` を取得する。追跡ブランチ（`@{upstream}`）は比較元に使わない。push 済みのフィーチャーブランチでは追跡先が同じブランチのリモートコピーになり、差分が空になってレビュー対象を取りこぼす。

未コミットの変更がある場合は `git diff HEAD` も取得し、作業ツリーの変更を範囲に加える。このレビューはコミット前に走ることが多い。

ベースとの差分と作業ツリーの変更がどちらも空の場合は、コードベース全体をレビュー範囲とすることをユーザーに確認する（AskUserQuestion などが使える環境ではそれを使う）。承認されたら全体をレビュー範囲とし、承認されなければ終了する。確認なしに範囲を広げない。

採用したベースと実際のレビュー範囲を最終報告に明記する。どの経路で範囲が決まったかが見えないと、想定より狭い範囲をレビューしたことに気づけない。

## 4観点のレビュー

レビュー範囲を再利用、単純化、効率、抽象度の4観点でレビューする。各観点は他の観点の結果を参照せず、独立にレビュー範囲全体を見る。

実行形態は環境によって決まる。

- サブエージェントを起動する手段がある環境では、4観点を1メッセージでまとめて起動し、並列に実行する。各サブエージェントにはレビュー範囲（差分、または全体レビューではその指定）と担当する1観点だけを渡す。
- その手段が無い環境では、4観点を順に自分で実行する。この場合は最終報告に、並列実行ではなく逐次実行したことを明記する。

各観点は指摘ごとに、ファイル、行、1行の要約、そして具体的なコスト（何が重複しているか、何が無駄になっているか、何が保守しにくくなるか）を返す。

### 再利用

レビュー範囲が含む、既存実装の焼き直しを指摘する。共有モジュールとレビュー範囲の近傍ファイルを検索し、代わりに呼ぶべき既存の実装を名指しする。

### 単純化

レビュー範囲が含む不要な複雑さを指摘する。冗長な状態や他から導出できる状態、わずかな差異を持つコピー＆ペースト、深いネスト、置き去りにされた死んだコードが対象で、同じ仕事をする、より単純な形を示す。

### 効率

レビュー範囲が含む無駄な処理を指摘する。重複した計算や繰り返しの I/O、直列に並べられた独立処理、起動処理やホットパスに置かれたブロッキング処理が対象で、より安価な代替を示す。

クロージャや捕捉した環境から作られる長寿命オブジェクトも対象とする。これは囲みスコープ全体をオブジェクトの寿命だけ延命させ、そのスコープが大きな値を保持している場合はメモリリークになる。必要なフィールドだけを複製するクラスや構造体への置き換えを示す。

### 抽象度

レビュー範囲の各実装が適切な深さにあるかを確認する。共有基盤の上に積まれた特殊ケースは、修正が浅すぎることの兆候であり、特殊ケースの追加ではなく基盤側の一般化を示す。

## 修正の適用

4観点すべての結果が揃ってから着手する。同じ行、または同じ仕組みを指す指摘は1件に統合する。

残った指摘は、その場でコードを直す。次のいずれかに当たる指摘は直さず、スキップした事実を記録する。指摘への反論は書かない。

- 修正が、意図された挙動を変えてしまうもの
- 修正が、レビュー範囲から大きく外れた変更を必要とするもの
- 誤検知と判断したもの

最後に、直したものとスキップしたものを短くまとめる。指摘が1件も残らなかった場合は、コードがすでに整っていることを述べる。
